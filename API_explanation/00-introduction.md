<h1 id="зачем-придумали-столько-способов-делать-api">Зачем придумали столько способов делать API?</h1>
<h2 id="мини-словарь">Мини-словарь</h2>
<p>Термины, которые встречаются в серии. Если что-то из этого уже знакомо - можно смело пропускать.</p>
<ul>
<li><a id="client"></a><strong>Клиент</strong> - тот, кто отправляет запрос. Браузер, мобильное приложение, скрипт, другой сервер.</li>
<li><a id="server"></a><strong>Сервер</strong> - тот, кто принимает запрос и отвечает. Обрабатывает логику и возвращает данные.</li>
<li><a id="endpoint"></a><strong>Endpoint (эндпоинт)</strong> - конкретный адрес, по которому принимаются запросы. <code>/users/42</code> и <code>/users</code> - два разных эндпоинта.</li>
<li><a id="resource"></a><strong>Ресурс</strong> - сущность, которой оперирует API (пользователь, заказ, пост).</li>
<li><a id="http-method"></a><strong>HTTP-метод</strong> - глагол запроса: например, <code>GET</code> - прочитать, <code>DELETE</code> - удалить. Говорит, что мы хотим сделать с ресурсом.</li>
<li><a id="status-code"></a><strong>Статус-код</strong> - число в ответе, которое говорит, чем закончился запрос. Например, <code>200</code> - успех, <code>404</code> - не найдено.</li>
<li><a id="json"></a><strong>JSON</strong> - текстовый формат данных, в котором чаще всего приходят ответы. Машино- и человекочитаем.</li>
<li><a id="contract"></a><strong>Контракт</strong> - формальное описание API: какие запросы бывают, что в них передаётся, что приходит в ответ. В разных подходах описывается по-разному: где-то в WSDL, где-то в OpenAPI, где-то прямо в коде.</li>
</ul>

<li><a href="02-soap.md">SOAP: тяжёлая артиллерия корпораций</a> - строгий контракт, WSDL, встроенная безопасность. Почему SOAP жив в банках и ненавидим в вебе.</li>
<li><a href="03-rest.md">REST: революция простоты</a> - ресурсы вместо действий, семантика HTTP. Over-fetching и under-fetching как цена простоты.</li>
<li><a href="04-graphql.md">GraphQL: запрос от клиента</a> - один эндпоинт, клиент сам выбирает поля. Как решает проблемы REST и какие сложности добавляет.</li>
<li><a href="05-grpc.md">gRPC: бинарный протокол</a> - Protocol Buffers, HTTP/2, стриминг. Почему RPC вернулся и где он выигрывает у REST.</li>

<h2 id="что-такое-api">Что такое API</h2>
<p>API (Application Programming Interface) - это интерфейс, через который одна программа обращается к другой. Вы знаете, какие запросы можно отправить и что придёт в ответ, а чужой код - это чёрный ящик. Думать об этом удобно как о <a href="#contract">контракте</a>: обе стороны договорились, что допустимо, и не лезут во внутренности друг друга. Популярная аналогия - меню в ресторане.</p>
<p>API повсюду, где две программы взаимодействуют: мобильные приложения и сайты тянут данные с сервера, микросервисы общаются друг с другом, оплата идёт через Stripe, карты - через Google Maps, а вход - через Google.</p>
<p>Например, клиент отправляет запрос по адресу:</p>
<pre class=" language-http"><code class="prism  language-http">GET /users/42
</code></pre>
<p>Сервер отвечает данными в JSON:</p>
<pre class=" language-json"><code class="prism  language-json"><span class="token punctuation">{</span> <span class="token string">"id"</span><span class="token punctuation">:</span> <span class="token number">42</span><span class="token punctuation">,</span> <span class="token string">"name"</span><span class="token punctuation">:</span> <span class="token string">"Alice"</span> <span class="token punctuation">}</span>
</code></pre>
<p>Любой API-вызов состоит из:</p>
<ul>
<li><strong>URL</strong> - куда обращаемся (<a href="#endpoint">см. эндпоинт</a>).</li>
<li><strong>Метод</strong> - что делаем (<a href="#http-method">см. HTTP-метод</a>).</li>
<li><strong>Тело</strong> - данные, которые отправляем.</li>
<li><strong>Заголовки</strong> - метаданные: формат, авторизация, язык.</li>
<li><strong>Ответ</strong> - <a href="#status-code">статус-код</a> и данные.</li>
</ul>
<p>Не все API выглядят так, как в примере выше. В RPC-подходе адрес один, а действие указано в теле. В SOAP тело обёрнуто в XML. В gRPC данные бинарные. Именно эти различия разберём.</p>
<h2 id="о-чём-эта-серия">О чём эта серия</h2>
<p>API не появились одномоментно: каждый подход решал боль предыдущего и приносил новые компромиссы. Покажем, почему современные API выглядят именно так.</p>
<p>Это не инструкция «как написать API» и не справочник. Это объяснение: откуда что взялось и почему.</p>
<p>В каждой статье есть блок сравнения: как выглядел запрос раньше и как теперь.</p>
<h2 id="что-вы-получите-(кроме-ответа-на-главный-вопрос-серии)">Что вы получите (кроме ответа на главный вопрос серии)</h2>
<ul>
<li>объяснение разницы между RPC, SOAP, REST и GraphQL на примере одного запроса;</li>
<li>понимание, какую проблему решает каждый подход и какую создаёт;</li>
<li>знания для выбора стиля API под задачу, а не по привычке.</li>
</ul>
